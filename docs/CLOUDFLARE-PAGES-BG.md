# DIDO v0.3 — публикуване и управление от телефон

Проектът е подготвен за **Cloudflare Pages с официалната GitHub интеграция**, на безплатен `*.pages.dev` адрес. Тази промяна не създава Cloudflare проект, не публикува сайт и не слива PR #1. `main` още не съдържа новата версия.

## Кой клон се използва

| Етап | Pages CMS | Cloudflare production |
| --- | --- | --- |
| Сега, подготовка и редакции | `feat/dido-v0-1` | Не създавай deployment |
| След одобрения финален преход | `main` | `main` |

Клонът в Pages CMS се избира от интерфейса, а не от `.pages.yml`. Конфигурацията не може да принуди hosted CMS да записва в конкретен клон. Проверявай избрания клон в горната част на CMS и запази отметка към версията с `main` след прехода. Стар CMS прозорец може да остане върху работния клон.

## Безопасен преход към main — еднократно, когато решиш да публикуваш

1. **Дотогава не свързвай проекта с Cloudflare.** Първото **Save and Deploy** създава публичен адрес. Preview deployments също могат да са публични. Не използвай работния клон за production и не създавай отделно копие на сайта.
2. Спри за кратко записите в Pages CMS и затвори отворените редактори, включително на друг телефон/компютър. Това предотвратява запис в стария клон след сливането.
3. В GitHub отвори [PR #1](https://github.com/Dido-hub-create/dido-website/pull/1). Провери, че посоката е `feat/dido-v0-1 → main`, че последните CMS commits са включени и че **Проверка на сайта / verify** е успешна за последния commit. Ако проверките още работят, изчакай. Ако `main` е променян и има конфликт, първо разреши конфликта в този PR и повтори проверките; не презаписвай `main` и не копирай записите ръчно.
4. За допълнителна възможност за връщане можеш от GitHub → списъка с branches да създадеш branch `backup/dido-before-main-v03` **от актуалния `feat/dido-v0-1`**. Ако името вече съществува, избери ново. Това запазва snapshot без да дублира публикации в сайта.
5. В **Files changed** провери оригиналната статия, четирите JPG снимки, състезанието `kaylakamarathon2026.json`, маршрута `kaylaka-21km-2026.json` и изходния GPX. Имената им не се променят. Не създавай повторно тези записи през CMS.
6. Едва след окончателното ти решение отбележи draft PR като готов и го слей през GitHub. Предпочети **Create a merge commit**, ако е налично, за да запазиш историята. Това действие е за собственика; Codex не го е извършил. Не изтривай работния/резервния клон преди проверката след прехода.
7. В Pages CMS избери **същото хранилище → branch `main`**. Провери наличните публикации, снимки, рекорди, състезание и маршрут. Запази нова отметка. Занапред редактирай тези записи, вместо да създаваш техни копия. Промененото заглавие на съществуващ запис не променя името на файла или адреса му.
8. Сега следвай настройките на Cloudflare по-долу. Така първият публичен deployment ще използва готовата версия в `main`, без предварително публикуване на работния branch.

Ако вече имаш Cloudflare Pages проект за това хранилище, не създавай втори: преди сливането изключи **Enable automatic production branch deployments** и избери **Preview deployments: None**. Това спира новите автоматични builds, но не скрива вече публикуван сайт. След проверката на `main` задай production `main`, включи автоматичните production deployments и пусни deployment на актуалния `main`, когато си готов.

## Настройване на Cloudflare от телефон

Използвай браузъра на телефона. При скрити полета включи „Версия за компютър“ от менюто на браузъра.

1. Влез в [Cloudflare Dashboard](https://dash.cloudflare.com/). Използвай **Free**; не добавяй платен план или домейн.
2. Отвори **Workers & Pages → Create application → Pages → Connect to Git** (в някои версии: **Import an existing Git repository**). Избери **Pages**, а не Worker или Direct Upload.
3. Свържи GitHub акаунта **Dido-hub-create**. При инсталиране на **Cloudflare Workers & Pages** избери **Only select repositories → dido-website** и разреши достъпа. Не е нужен API token.
4. Избери repository **Dido-hub-create/dido-website → Begin setup**. Попълни:

| Поле | Точна стойност |
| --- | --- |
| Project name | `dido-website` (ако е заето: `dido-website-bg` или друго свободно име) |
| Production branch | `main` — само след финалното сливане |
| Framework preset | `Astro` |
| Root directory / Path | остави празно — коренът на хранилището |
| Build command | `npm run build` |
| Build output directory | `dist` |
| Environment variable → Name | `NODE_VERSION` |
| Environment variable → Value | `24.22.1` |
| Environment variable → Name | `ASTRO_TELEMETRY_DISABLED` |
| Environment variable → Value | `1` |

Добави променливите за **Production**, а ако интерфейсът предлага и Preview — същите стойности и там. Не добавяй deploy command, API ключове, D1, R2, Workers Functions, адаптер, Wrangler или build hooks. Cloudflare инсталира npm зависимостите от `package-lock.json` автоматично. Нужен е съвременният build image с поддръжка на Node 24; ако е показан избор на build system, използвай актуалния **v3**, не legacy image.

5. **Save and Deploy е първото реално публично публикуване.** Натисни го само когато си готов. Полученият адрес ще е например `https://dido-website.pages.dev`; действителното свободно име се показва от Cloudflare.
6. В проекта → **Settings → Builds & deployments** (или **Builds → Branch control**) задай:

| Поле | Стойност |
| --- | --- |
| Production branch | `main` |
| Enable automatic production branch deployments | включено |
| Preview deployments / Preview branch | `None` |
| Build watch paths | всички файлове; без изключване на `src/content`, `src/data`, `public` или `.pages.yml` |

Ако Preview изборът е наличен още при създаване, задай `None` там. Ако не е — задай го веднага след първия deployment, преди нови commits в други branches. Запази настройките. Не е необходим custom domain.

7. В **Deployments** изчакай **Success** и провери, че branch е `main`, а commit-ът съвпада с последния в GitHub. При неуспешно обновяване предишната успешна версия остава активна; отвори build логовете от телефона.
8. На `pages.dev` провери началната страница, оригиналната статия и снимките, мобилното меню, състезанието „Маратон Кайлъка 2026“, отброяването, картата и изтеглянето на маршрута. Файлът трябва да се казва `maraton-kaylaka-2026-21km.gpx`, а името на трасето вътре да е „Маратон Кайлъка 2026 – 21,1 км“.

## Всекидневна работа — без терминал

Отвори [Pages CMS](https://app.pagescms.org/), влез с GitHub и избери **Dido-hub-create/dido-website → main**. Записът прави commit; Cloudflare автоматично изгражда сайта и заменя активната версия след успешен build. Не са нужни `git pull`, Codespaces, рестарт или Codex. Изчакай Success, преди да очакваш промяната на сайта. Няколко последователни записа могат да стартират няколко builds.

- **Публикации:** заглавие, текст, снимки/галерия, раздел, тема, дата и статус. Редактирай съществуващия запис, когато обновяваш статия.
- **Състезания:** дата, час, часова зона, статус, снимки, бележки и връзки. Отброяването работи в браузъра и не изисква нов build всяка секунда.
- **Моите маршрути:** качване на GPX, заглавие, снимки, премахване на начало/край и отделните разрешения за публикуване, карта и изтегляне. Името за изтегляне се получава от заглавието; вътрешният URL `trace.gpx` остава същият. `21,1 км`/`21.1 km` в името става `21km` по договорения пример; координатите и измерената дистанция не се променят.
- **Настройки на сайта:** име (DIDO), подзаглавие (Личен сайт), изображение за лого, шестте надписа на менюто, досегашните текстове, снимки, кадриране, контакти и рекорди. Празно лого връща текстовото лого; липсващо локално изображение също използва текста. Празни име/подзаглавие/надпис връщат стойността по подразбиране. Адресите на разделите остават фиксирани. Използвай кратки надписи, за да се побират удобно на телефон.

CMS генерира новите имена от дата, час и безопасен slug на заглавието; ръчното поле за име при създаване е скрито. Съществуващите имена и връзки не се мигрират. Съзнателното създаване на втори запис със същото съдържание пак е възможно — за обновяване използвай редактиране.

## Ако се появи неправилно име

Имена като `MarathonKaylaka21km.gpx.json` не се поправят автоматично и не получават нов идентификатор. Само този запис се пропуска; останалият сайт продължава да се изгражда. Невалиден JSON обект, символна връзка, прекалено голям запис и конфликт между имена с различен регистър също се пропускат. Неправилно именуван Markdown файл не се подава на Astro за обработка. Диагностиката е в **Cloudflare → Deployments → build logs** с префикс `[DIDO content]`, име на файла и причина; не отпечатва съдържание или координати.

От списъка в CMS използвай менюто **⋯ → Rename**, ако е налично, и поправи **съществуващия** файл до например `kaylaka-21km-2026.json` (само букви, цифри, тире/долна черта и едно `.json`). Ако CMS версията няма Rename, използвай GitHub през браузъра: правилния branch → съществуващ файл → Edit → поправи името → Commit changes. Не създавай копие и не презаписвай вече съществуващ файл. Ако променяш идентификатор, обнови свързаните записи чрез reference полетата в CMS. В настоящия проект проблемът вече е поправен в съществуващия route; няма втори Кайлъка запис за пренасяне.

Защитите за GPX остават: изрично публикуване и одобрение, отделни разрешения, премахване на участъци/лични метаданни, еднаква обработена геометрия за карта и download, забрана за изходен GPX в `public/`, проверки за traversal и символни връзки. Опасен GPX в `public/` продължава да спира build-а. Публичната карта технически разкрива координатите си. GitHub хранилището е публично: оригиналите в него остават публични независимо от CMS статус; качвай само предварително одобрени за споделяне файлове. Подробности: [DIDO v0.2](DIDO-v0.2.md).

## Съвместимост и ограничения на Free

Astro е конфигуриран с `output: static` и `trailingSlash: always`. Няма сървърна зависимост. HTML, изображенията, локалният Manrope, JavaScript картата/броячите, `map.json` и разрешените GPX влизат в `dist/`. Leaflet използва досегашните OpenStreetMap плочки без API ключ; интернет връзка е нужна за плочките. `404.html` запазва поведението за несъществуващи адреси. Генерираният `dist/_headers` задава правилното име за директно изтегляне през Cloudflare; HTML бутонът задава същото име.

Astro 7.4.7 изисква Node **≥22.23.4**. Проектът и CI са фиксирани към **24.22.1** чрез `.nvmrc`; използвай същата стойност в `NODE_VERSION`. Не използвай Node 18/20 или общо „Node 22“ без проверка на patch версията.

Free има квоти: **500 builds/месец**, **1 build наведнъж**, **20 минути/build**, **20 000 файла**, **25 MiB/файл**. `_headers` допуска **100 правила**; текущият сайт използва едно правило за един разрешен GPX. Ако библиотеката достигне този лимит, е нужна промяна на техническия формат за download адресите, преди да се добавят още правила. Не са необходими платени услуги за текущия проект. Избягвай автоматично платено надвишаване.

Проверки за разработчик: `npm ci` и `npm run verify` (CMS, Astro/TypeScript, build, тестове). CI прави същото и запазва artifact; няма deployment workflow. Локалните проверки не заместват първия преглед в Cloudflare/CMS и GPS приложение.

Официални източници: [Astro в Pages](https://developers.cloudflare.com/pages/framework-guides/deploy-an-astro-site/), [build настройки](https://developers.cloudflare.com/pages/configuration/build-configuration/), [GitHub интеграция](https://developers.cloudflare.com/pages/configuration/git-integration/github-integration/), [branch controls](https://developers.cloudflare.com/pages/configuration/branch-build-controls/), [HTTP headers](https://developers.cloudflare.com/pages/configuration/headers/), [Free квоти](https://developers.cloudflare.com/pages/platform/limits/), [CMS конфигурация](https://pagescms.org/docs/configuration/).
